# test/

Host-buildable Unity test suites for the logic in [core/](../core/README.md) and the parts of [gui/](../gui/README.md) that do not draw — no hardware, no LVGL rendering. These build and run entirely on the host machine: `core/`, `gui/screens/layout.cpp` and `gui/screens/zoom_cycle.cpp` have no Arduino/SDL/LVGL-rendering dependency at all, and `gui/theme` and `gui/bindings` need LVGL's headers and font data but never a display.

```sh
pio test -e simulator
```

Running tests overwrites the simulator environment's build output — run `pio run -e simulator` afterward to restore the interactive simulator binary before using it again.

## Suites

- **`test_core_config/`** — [core/config](../core/config/README.md)'s `ConfigStore` and [core/vehicle](../core/vehicle/README.md)'s `evaluate_warning()`: defaults on blank storage, save/load round-trips (including `display_mode` and partial `save_priority`/`save_signal` writes), and falling back to defaults on an unrecognized config version.
- **`test_core_vehicle/`** — [core/vehicle](../core/vehicle/README.md)'s `SignalStore` and [core/time](../core/time/README.md)'s `Scheduler`: single- and multi-request signal round-trips (a multi-request signal doesn't resolve until *all* its requests report), unit-conversion/display-value correctness, that every catalog entry's `display_min < display_max`, metric↔imperial round-tripping, and that the scheduler actually fires tasks once they're due.
- **`test_gui_layout/`** — [gui/screens](../gui/screens/README.md)'s `compute_layout()` and `compute_prominence_ranks()`, across both `LayoutStyle`s. A **golden table** captured from the implementation as it stood before the style axis existed asserts every `Grid` slot for every count and orientation by value — the other cases here assert *properties* (tiling, transposition, clamping) which a subtly different but self-consistent shape could still satisfy, so the golden is what actually protects the MQB product from the new axis. For `Strip`: equal full-height bands, complete tiling for every divisor of `BAND_UNITS`, falling through to `Grid` for an indivisible count, no hero at count 3 (so ranks run plain left-to-right), a count of 1 still being a hero (the zoom view, which needs the largest font), and vertical being a true transpose.

  Also `ZoomCycle`, the short-press cycle that replaces "promote to hero": that it starts on the overview, visits every rank exactly once before returning (four positions for three signals — anything else and the gesture either skips a gauge or needs pressing a different number of times than there are panels), wraps indefinitely, is **inert on a single-panel overview** (zooming into rank 0 from a one-panel overview is the same view twice, so the cycle would have a step where the button visibly does nothing), returns to the overview when the panel count changes, and never produces a rank offset that runs off `priorities[]`. Plus the original coverage — the exact shape of each panel count (1 full-screen, 2 equal columns, 3 hero+stack, 4 even 2×2, 5 matching the legacy fixed layout, 6 even 2×3), that every count's slots fully tile the grid with no gaps/overlaps, that vertical orientation is a true transpose of horizontal (including prominence ranks) for every count except 5 — which gets its own bespoke Vertical shape (a 2×2 of small panels over one wider, higher-priority panel), covered by its own dedicated tests instead — that an out-of-range count gets clamped to 1–6, and that priority rank 0 always resolves to the most prominent slot (hero > large > small) regardless of raw slot index.
- **`test_gui_theme/`** — that the fonts a theme names actually fit the panels its metrics describe, measured against the real font data. This exists because the build plan's font recommendation was wrong: it sized the gauge readout assuming a three-character worst case, but Pressure carries two decimals in metric and one in imperial, making it five (`10.34` bar, `150.0` psi) — 138 px of `bold_46` in a 98 px panel. A clipped value is not something a code review catches, and only shows up in the simulator once a signal happens to reach a wide enough number, so the arithmetic is asserted instead. Also checks the *vertical* fit, that the next font size up genuinely would not have fit (so the choice is not gratuitously small), and that `THEME_DEFAULT`'s geometry and font ladder are untouched.

  It then got a second lesson from the same place. The fit check measured the value and stopped there — but a panel also draws a unit tag, normally to the right of a value that is itself centred, so the pair overhangs the centre line by half the value plus the whole tag. `77.2 psi` rendered as `77.2 ps` on a build where every assertion in this file was green. `Metrics::unit_stacked` is the fix, and the suite now asserts the rule that applies to *each* theme rather than one rule for both — including that side-by-side genuinely would not fit on the gauge product, so the stacking is not left in place out of habit once it stops being needed.

- **`test_gui_bindings/`** — [gui/bindings](../gui/bindings/README.md)'s `VehicleBinding`, and specifically where a panel's warning highlight comes from. That the default path is the unchanged stateless evaluation; that with a `core::WarningLatch` attached a warning survives the value recovering while the *reading* still tracks the current value (the highlight is a memory, the reading never is); that a blanked signal reads `--` even while a latch is still showing the warning that fired before the wire came loose; and that **drawing a panel never advances the latch**, which is the whole reason the binding reads rather than drives.

  That last one is worth a note on how to write it. The first version set `qualify_ms` to 500 and passed against a binding that *did* drive the latch, simply because the timestamp such a binding would pass in never advanced. Setting `qualify_ms` to 0 — so a driven latch would raise on the very first sample it was given — is what makes the assertion mean anything.

- **`test_core_input/`** — [core/input](../core/input/README.md)'s gesture machine, chord recogniser and action map, driven over a synthetic timeline so a whole press-hold-release sequence is deterministic. Expected instants are computed from `GestureTimings` rather than written as literals, so moving a threshold moves the tests with it. Covers: a contact bouncing for 10 ms producing exactly one press (and the same on release, which is where phantom double-presses come from); single-vs-double disambiguation on both sides of the window boundary, with the single firing exactly when the window closes rather than whenever the second press happened to arrive; hold-repeat cadence; **that a very-long press never also reads as a click** — the classic bug in this kind of machine; that a dropped frame slows the ramp instead of paying back every missed interval one-per-poll when the loop recovers; a button held at boot being ignored until released; and a board with no buttons staying silent.

  For chords: pressing both together emits **one** chord and no individual long presses *and no clicks on release*, while pressing one, holding it past the threshold and then pressing the other emits **two** independent long presses and no chord. Plus the claim the whole chord design exists to make true — `test_a_short_press_is_not_delayed_by_having_a_second_button` runs the identical sequence on a one- and a two-button board and asserts the same instant.

  For the action map: the default resolution, that a latched warning pre-empts discrete presses but *not* repeats, that rebinding replaces rather than shadows, and — asserted rather than left implicit — exactly which actions a single-button board cannot reach. Plus `load()`, the persistence read side: a full round trip, that it *replaces* rather than merges (merging would resurrect a gesture the owner deliberately removed), and that a malformed saved table — duplicates, a count past capacity, a null pointer — is survived rather than trusted.

- **`test_core_sensors/`** — [core/sensors](../core/sensors/README.md)'s conditioning maths and `AnalogSignalSource`. Two kinds of test live here. The ordinary kind covers divider maths, the two-point fit across three different output spans (0.5–4.5, 0–5, 1–5 V) to prove nothing about any one sender is hardcoded, a descending sender, all three curve models against independently-derived reference points, LUT interpolation at, between and *beyond* both endpoints, EMA step response against its time constant, that the time constant is independent of sample cadence, and that the median rejects a single-sample spike.

  The second kind closes the loop with the simulator, whose sensor model is written **backwards** — waveforms scripted in psi and °C, then pushed through the *inverse* of each transfer function to produce ADC volts. `test_conditioning_recovers_the_simulators_scripted_values` runs core/sensors forwards across a full 180 s warmup cycle and asserts it lands back on the original numbers. A simulator emitting convenient voltages directly would let a wrong transfer function pass.

  And the plausibility cases, which are the reason the module exists: an open thermistor leg is rejected rather than reported as a believable −86 °C, a disconnected transducer input (which drifts to 0 V and *is* arithmetically fine) is rejected by the band derived from its own 0.5 V offset, re-calibrating a channel moves that band with it, and in both cases the store sees **no write at all** — not a zero, not even a refreshed timestamp on the old value, since a moving timestamp would make a dead sensor look alive to `core::Logger`.

- **`test_core_device_config/`** — [core/device_config](../core/device_config/README.md)'s `DeviceConfigStore`, the gauge product's second blob (sensor calibrations and the button map).

  The interesting cases here are all *rejection* cases. A display setting read back wrong shows the wrong number of panels; a sensor calibration read back wrong makes a gauge report a plausible, confident, incorrect oil pressure — the single failure the whole conditioning layer exists to prevent. So the suite covers each header field disagreeing in turn (version, `struct_size`, `catalog_count`, and both counts), and asserts that a rejected blob leaves **nothing** partial behind rather than a half-read calibration.

  It also separates the two ways a load can come back empty: erased storage is an ordinary first boot, while a blob of ours that disagrees about its shape means somebody's calibration was just discarded — and the composition root needs to tell them apart, because only the second is worth mentioning. Plus the partial writers landing on the right channel (getting that offset arithmetic wrong overwrites a *neighbouring* sensor's curve, silently), a partial binding write carrying its count out of the header, and a backing store too small to hold the blob saying so instead of looking like a device that boots fresh forever.

- **`test_core_logging/`** — [core/logging](../core/logging/README.md)'s `Logger`: boot recovery on blank storage, on-change dedup (a signal re-polled at the same value produces no new record, even though its `last_update_ms` advanced), the `LOG_MIN_INTERVAL_MS` rate floor in both directions (a signal arriving at half the floor is spaced out to exactly the floor; a slower one is left at its own cadence — both asserted against the constant rather than a literal cadence, so the test survives the floor moving), scoping to the displayed panel set (a signal with fresh data that isn't on a panel never reaches the log), priming on reassignment (a newly-displayed signal's pre-existing value is taken as a baseline, never written), flush triggering, chunk rotation/wraparound (overwriting the oldest slot with newer data), the capture index (each on/off cycle counting as its own log, surviving a reboot, dropping out of the count once the ring laps past it, and self-healing from a corrupt index), lazy chunk creation (repeated boots with the recorder off must evict nothing), `used_bytes()` climbing monotonically to capacity and pinning there once the ring laps, and self-healing recovery when one chunk's header is corrupt/foreign. Chunk sizing is overridden to tiny values via `Logger`'s test-only constructor args — the real ~13MB production budget would make a wraparound test write tens of megabytes per run.

## Adding a test

Follow an existing suite's shape: a `test_main.cpp` with one `void test_*()` per case, `RUN_TEST()`'d from `main()`/`setup()`. A new suite needs its own subdirectory under `test/` (PlatformIO's Unity runner discovers one binary per subdirectory) — see the two existing `core/` suites for how to construct fakes for `IConfigStore`/`IClock`/`ICanBus` without any real platform.
