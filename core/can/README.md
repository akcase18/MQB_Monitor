# core/can/

`core::UdsClient` — the UDS (Unified Diagnostic Services) enhanced-diagnostic-session request/response protocol, layered over the platform-provided `ICanBus`. This is protocol logic only: it doesn't own any timers or request scheduling (`core::SignalPoller` in [core/vehicle](../vehicle/README.md) decides *what* to ask for and *when*) and it doesn't know which signal a response belongs to (also [core/vehicle](../vehicle/README.md)'s job).

## Files

- **`inc/uds_client.hpp`** / **`src/uds_client.cpp`** — `UdsClient`:
  - `UdsEcu { tx_id, rx_id }` — one module: the CAN id it's asked on and the one it answers on. The client is built with a table of them (`UdsClient(bus, ecus, num_ecus)`); for the dash that's the generated `core::UDS_ECUS[]`.
  - `UdsRequestSpec { byte1, byte2, offset, scale, field, ecu }` — identifies one UDS data-by-identifier request, the module it goes to (an index into the ECU table), and how to decode its value: `field` says which bytes of the response payload are this request's, then `(raw + offset) * scale`.
  - `UdsField { start, len, is_signed, bit_shift, bit_len, little_endian }` — `len == 0` is the legacy auto decode (u8 for a 1-byte payload, else s16 from bytes 0–1); otherwise `len` (1–4) bytes from `start`, big-endian unless `little_endian` (most VW data is big-endian; some DIDs, like clutch torque 38 2E, aren't), optionally narrowed to a bit range, sign-extended at the field's width. Several signals can each read their own field out of one multi-value DID. `uds_decode_field(payload, len, field, out)` does the decode — mirrored by the monitor tool's `decode_field()`, and tested against the same vectors.
  - `send(spec)` — sends a request for the given `(byte1, byte2)` identifier pair to the spec's module.
  - `poll(cb, ctx, ncb, nctx)` — drains every pending response on the bus and invokes `cb(ctx, ecu, byte1, byte2, payload, len)` with each one's data bytes and the module that sent it. A frame on an id outside the ECU table is ignored. Nothing is decoded here, since one response may hold several signals' fields.
  - **ISO-TP.** A response too long for one frame arrives as a first frame and consecutive frames. `poll()` answers the first frame with flow control (`30 03 00`: blocks of 3, no gap), reassembles the rest, and sends another flow control after every 3 — the Teensy keeps only 4 received frames between `poll()` calls, so an unlimited burst would overwrite itself during an LVGL repaint. Payloads up to `UDS_MAX_PAYLOAD` (32) bytes; a longer one is refused with an overflow flow control (`32`). A missed or out-of-order frame drops the whole answer, and the poller asks again. `receiving()` is true while one is part-way in. The multi-frame code is FLASHMEM: it only runs for DIDs too long for one frame.
  - Negative responses (`7F <service> <nrc>`) go to the optional `ncb(nctx, ecu, service, nrc)` instead, and are dropped when it's null. They name no data identifier — the ECU only echoes the service it's rejecting — so only a caller tracking its own outstanding request can attribute one, which is exactly what `SignalPoller` does with it.

- **`inc/slcan.hpp`** / **`src/slcan.cpp`** — SLCAN (LAWICEL ASCII), the serial-CAN protocol [`tools/monitor`](../../tools/monitor/README.md) speaks. `encode()` turns one `SniffFrame` into its `t`/`T` line; `Session` interprets host command lines (`Sn`, `O`, `L`, `C`, `t`/`T`, `Z`, `V`, `N`, `F`) against an `IPort` that does the bus and serial work, replying CR/BELL per the SLCAN convention. Shared by the standalone sniffer (`platform/teensy/tools/can_sniffer.cpp`) and the dash's own sniffer mode (`src/main.cpp`), so both answer the host identically. Everything here is FLASHMEM, `encode()` included: on the dash it only runs while sniffing, with the dashboard paused.

## Usage

`src/main.cpp` constructs one `UdsClient` over the generated ECU table (`core::UDS_ECUS[]` — the engine's `0x7E0`/`0x7E8` plus any other module an active signal reads), opens the bus at 500 kbps to receive the range of their response ids (`core::uds_ecu_rx_range()`), and calls `poll()` once per `loop()` iteration, immediately before `SignalPoller::tick()` — drain first, send second, so a response arriving this iteration frees the poller's in-flight slot in time for it to send the next request in the same pass. Every response it decodes is handed to `core::SignalStore::on_uds_response()` (see [core/vehicle](../vehicle/README.md)), which is where `(ecu, byte1, byte2)` actually gets matched back to a signal, *and* to `SignalPoller`, which is what closes the flow-control loop.
