# core/config/

The persisted configuration schema and its load/save/migrate logic, storage-agnostic over the platform's `IConfigStore` (EEPROM on Teensy, a file on the simulator — see [platform](../../platform/README.md)).

## Files

- **`inc/config.hpp`** — the schema:
  - `ConfigHeader { magic, version }` — versioning/validity check, written by `ConfigStore`.
  - `Settings { day_brightness, night_brightness, num_panels, brightness_mode, orientation, logging_enabled, flipped_horizontal, flipped_vertical, open_orientation_on_boot, accent_color, auto_brightness_pct }` — global settings, edited from the Settings screen. `logging_enabled` gates [core/logging](../logging/README.md)'s `Logger` entirely and defaults **off**: capture is a deliberate "record this drive" action, not something that should burn flash write-cycles on every commute. It's toggled from `LoggingScreen` (swipe up from the dashboard), not from the Settings screen — see [gui/screens](../../gui/screens/README.md). `brightness_mode` (`BrightnessMode::{Day, Night, Auto}`) is which level the backlight shows; Auto follows the car's dimmer through [core/vehicle](../vehicle/README.md)'s `AutoBrightness`, starting from (and falling back to) `day_brightness`. `auto_brightness_pct` is Auto's slider, 0–100: `AUTO_BRIGHTNESS_NEUTRAL` (50, the default) shows the dimmer's level as it is, either end shifts it by up to 25%.
  - `PrioritizedSignal { signal_id, units, display_mode }`, one per priority rank (`MAX_PANELS = 6`) — which signal is the Nth most important, in which unit system, drawn how. Indexed by **priority rank** (0 = most important), not by screen slot — a signal's on-screen prominence follows its rank across every panel count, rather than being tied to whichever slot happened to be "panel 1". Resolve rank → slot via `gui::compute_prominence_ranks()` (see [gui/screens](../../gui/screens/README.md)) for the current panel count/orientation.
  - `SignalConfig { warn, use_custom_range, custom_min, custom_max, signal_id }` — one signal's `WarningThresholds` (see [core/vehicle](../vehicle/README.md)) and display-range override, tagged with the signal's id (`NO_SIGNAL_ID` = empty slot). Warning thresholds are keyed **by signal, not by rank** — so reassigning a signal to a different rank carries its thresholds with it automatically, instead of needing to be re-entered.
  - `Config { header, settings, priorities[MAX_PANELS], signals[SIGNAL_CONFIG_SLOTS] }` — the whole persisted blob (1884 bytes; the smallest `IConfigStore` is 4096). `signals[]` is a fixed 64 slots, so the stored layout doesn't depend on how many signals are active. Once loaded, `signals[i]` belongs to `SIGNAL_CATALOG[i]` for every catalog position, so callers index it by catalog position (resolved via `signal_catalog_find(id)`). The slots past the catalog keep the settings of signals this build doesn't have, so demoting a signal and promoting it again gets its thresholds back.
  
  `MAX_PANELS` (6) is a fixed compile-time capacity; `Settings::num_panels` is the *active* count within it (1–6) — unused ranks are simply inactive, not compiled out.

- **`inc/config_store.hpp`** / **`src/config_store.cpp`** — `ConfigStore`:
  - `MAGIC_NUMBER` / `CURRENT_VERSION` (currently 10: v2 added `PanelConfig::display_mode`, v3 added `Settings::accent_color`, v4 added `SignalConfig`'s custom-range fields, v5 renamed `Config.panels[]` (screen-slot-indexed) to `Config.priorities[]` (priority-rank-indexed), v6 added `Settings::logging_enabled`, v7 made `signals[]` a fixed table of id-tagged records instead of one positional record per catalog entry, v8 added `Settings::brightness_mode`, v9 added `Settings::auto_brightness_pct`, growing `Settings` from 16 to 20 bytes and moving everything after it, v10 added `Settings::log_source` in padding and the log profile — `log_count` and `log_signals[MAX_LOG_SIGNALS]`, signal ids a Profile capture records — after `signals[]`) gate loading. On load, profile ids this build doesn't offer, and repeats, are dropped (`fix_log_profile()`).
  - `load()` — unrecognized magic → `set_defaults()` (and persists them); older version → `migrate()` (and persists the result); current version → full load, then the signal records are sorted back into catalog order (each found by id; a newly promoted signal gets a fresh record), an out-of-range `brightness_mode` becomes Day and an out-of-range `auto_brightness_pct` 50, and it's saved if anything changed; newer version (firmware this board has rolled back from, see [platform/dash_s3/OTA_PLAN.md](../../platform/dash_s3/OTA_PLAN.md)) → defaults, **not** persisted, so reinstalling the newer firmware finds its config again — until something here saves.
  - `save()` — writes the entire `Config` back.
  - `save_priority(rank)` / `save_signal(signal_id)` — partial writes, so e.g. reassigning one rank or editing one signal's thresholds doesn't rewrite the whole blob. Over a newer firmware's config they do a full `save()` instead: one record written at this layout's offset, under a header still naming the newer version, would load as valid there.
  - `set_defaults()` — day/night brightness 100%/20% in Day mode, Auto's slider at 50, 5 active panels (rank 0 = Coolant Temp down through rank 4 = Intake Pressure Actual, with rank 5 = Engine Torque inactive by default), all warning thresholds off, green accent, logging off.
  - After any load or migration, a priority rank holding a signal this build doesn't offer (demoted to WIP or internal, or removed from the registry) is put back to that rank's default. Left in place it would show an empty panel, crash the phone page's panel tab, and make the dash reject the phone's Save.
  - `migrate(old_version)` — v9 is a prefix of v10 and reads straight in, with `log_source` set to Screen over what was padding and an empty profile. v6–v8 share a head: the header, a 16-byte `Settings` (the current one less `auto_brightness_pct`, which keeps its default), and the priorities at byte 20, with the signal records from byte 92. v7's and v8's records are the current id-tagged ones and read straight in. Before v8, `brightness_mode`'s byte was padding, so v6 and v7 get Day (padding was never guaranteed zero); v8 keeps its mode. v6, the version dashes in the field held longest, is carried across: settings and priorities read as they are, and each positional v6 record is tagged with the id of the signal at that position in the v6 catalog (a fixed list in `config_store.cpp`; that order never changed while v6 was current). v6's `brightness_mode` byte is set to Day too. Versions before 6 never left the bench, so they fall through to `set_defaults()`. A `static_assert` in `config_store.cpp` pins `sizeof(Config)` and its key offsets to `CURRENT_VERSION`, so a changed layout — a field added or moved, or `SIGNAL_CONFIG_SLOTS` raised — doesn't compile until the version is bumped and those numbers updated, which is the prompt to write the next step. Promoting or reordering signals isn't a layout change any more.

## Usage

`src/main.cpp` owns the one `ConfigStore` instance (inside its `Composition` singleton), calls `load()` once at startup, and passes it into `gui::VehicleBinding` (see [gui/bindings](../../gui/bindings/README.md)), which is the only code that reads/writes `Config` fields on behalf of the UI.
