# core/vehicle/

The vehicle-signal data model: a static, ROM-able catalog of every signal the dashboard can display, a runtime value store holding their current values, and signal-scoped warning-threshold evaluation.

**Nothing here knows how a value is acquired.** The catalog describes what a signal *is* — name, unit, display range; the store holds whatever the latest measurement was. How one is obtained lives in a per-product acquisition layer keyed by signal id: [core/can](../can/README.md) for the CAN product (`UDS_BINDINGS`, `UdsDecoder`, `SignalPoller`). That split is what lets a second product read the same signals from analog sensors without touching this directory, `core/config`, or any of `gui/`.

## Files

- **`data/<product>/signals.json`** — the **two-stage signal registry**, one per product. `data/mqb/` is the CAN car's; `data/gauge/` is the analog gauge's.

  **The two share no signals at all.** An MQB car has no way to report oil pressure, and the gauge has no bus to ask over, so this is two independent registries rather than one filtered two ways. `platformio.ini` puts exactly one product's `generated/` directory on the include path per environment — the same "configuration picks the file" mechanism `build_src_filter` already uses to pick a board, so there is still no `#ifdef` anywhere in `core/`.

  The MQB registry is also the single source of truth shared with the Mac monitor tool ([tools/monitor](../../tools/README.md)). Every signal ever defined lives in it, tagged `"status": "active"` or `"status": "wip"` (unconfirmed offset/scale, a placeholder name, etc.); [`tools/gen_catalog.py`](../../tools/gen_catalog.py) filters to `status == "active"` only, so WIP entries never reach the firmware. The monitor tool's Registry/Learn/WIP tabs are how you add, review, and promote/demote entries; edit the JSON and re-run the script (commit both) if you're doing it by hand instead.

  One filtered pass per product emits everything downstream of it — `generated/<product>/signal_catalog.generated.inc` (presentation), `signal_catalog_count.inc` (the count that sizes fixed arrays), `signal_defaults.generated.inc` (the factory panel assignment), and for a bus product [core/can](../can/README.md)'s `generated/<product>/uds_binding.generated.inc` (acquisition). Catalog entry *i* and binding entry *i* are the same signal, which holds by construction because both come out of the same pass. Only the unit helpers are hand-written here; the `transform_*` functions a signal's JSON `"transform"` field names live with the requests they combine, in core/can.

  Filtering **never reorders** the registry's own array order — active entries keep the same relative order they have in the file (`gen_catalog.py` just skips WIP ones, in place). The registry's order can still change, deliberately, via the monitor tool's Registry tab Move Up/Down (`Catalog.move_signal`). That's safe *today* only because `core::Config::signals[SIGNAL_CATALOG_COUNT]` (see [core/config](../config/README.md)) — a flat array persisted in flash, positionally indexed by the compiled catalog's array order (always resolved via `signal_catalog_find(id)`, never a raw index) — has never actually been written to a device (`ConfigStore::migrate()` is a no-op stub). Once a device has shipped with saved config, reordering active signals would misalign its already-saved on-device warning thresholds, and `migrate()` would need to stop being a no-op before that becomes routine.

- **`inc/signal_catalog.hpp`** / **`src/signal_catalog.cpp`** — `SIGNAL_CATALOG`, the *active* signals (generated from the product's registry, above), each a `SignalSpec`:
  - `id`, `name`, `unit_type` (`UnitType::{None,Degrees,Percent,Pressure,RPM,Speed,Temp,Torque,Volume}`).
  - `display_min`/`display_max` — full-scale bounds in the signal's native (metric) unit. These are sensible engineering defaults (e.g. coolant 0–250°F equivalent, boost -15–25psi), **not** per-vehicle-tuned — they scale a Bar/Gauge panel's fill and bound the warning-threshold editor's +/- range. Real per-car tuning is a planned future phone-app feature, not built here (see [TODO.md](../../TODO.md)).

  Also: `signal_catalog_find(id)`, unit-label/decimal-precision helpers, and metric↔imperial conversion (`unit_convert_to_imperial`/`unit_convert_to_metric`) used both for display and for converting warning thresholds edited in whichever unit system a panel is currently showing.

  The current catalog: Coolant Temp, Engine Oil Temp, Intake Air Temp, Ambient Pressure, Charge Pressure, Intake Pressure (Actual), Intake Pressure (Specified), Engine Torque, Engine Speed (RPM), Throttle Position, Vehicle Speed, Fuel Level, per-cylinder (1–4) Misfire Count and Timing Correction, and a combined Misfire Count.

- **`inc/signal_store.hpp`** / **`src/signal_store.cpp`** — `SignalStore`, the runtime value cache:
  - `set(id, value, now_ms)` / `set_at(idx, ...)` — the **only** write path. Means "somebody measured this signal, at this time", with no notion of where the number came from. [core/can](../can/README.md)'s `UdsDecoder` fills it from CAN responses; an analog sensor source on another product fills the same store the same way.
  - `get(id)` / `get_display_value(id, is_metric)` — read a signal's current `SignalValue` (raw value, `has_data` flag, last-update timestamp) or its unit-converted, precision-rounded display value.
  - `has_data` stays false until something writes, which is what stops a panel showing a number, or a warning firing, before the first real measurement. A source that declines to write — no UDS response yet, or an out-of-band analog reading — gets a blanked panel and a suppressed warning for free.
  - This class used to own `on_uds_response()` and a pair of per-request accumulator arrays. Both moved to `core::UdsDecoder`; see [core/can](../can/README.md) for why that mattered structurally.

- **`inc/signal_source.hpp`** — `ISignalSource`: `set_active(ids, count)` and `tick(now_ms)`. Where live values come from, as an interface — one implementation per acquisition method ([core/can](../can/README.md)'s `UdsSignalSource` today). Lives here rather than in `core/can` because there is nothing bus-specific about it: it names signals by catalog id and hands back nothing, so the dependency arrow keeps pointing the right way. Also carries `MAX_ACTIVE_SIGNALS`, the capacity guarantee every source inherits; it is tied to `core::MAX_PANELS` by a `static_assert` in `src/main.cpp`, the one file allowed to see both.

- **`inc/peak_hold.hpp`** / **`src/peak_hold.cpp`** — `PeakHold`: the highest and lowest each signal has reached since the last reset. Most of why somebody fits gauges — max oil temp over a drive, minimum oil pressure over a drive — since the number that matters is rarely the one on screen when you look down. Alongside `SignalStore` rather than inside it: the store means "this is the current value", and this is resettable state whose lifetime is a drive. **Only signals whose `has_data` is set are sampled** — that line is load-bearing, because an analog channel that fails its plausibility check declines to write, and a tracker that sampled it anyway would pin the minimum at 0.0 and leave "0.00 bar minimum oil pressure" on screen for the rest of the drive, sourced entirely from a loose connector.

- **`inc/warning_latch.hpp`** / **`src/warning_latch.cpp`** — `WarningLatch`: holds a warning until acknowledged, and refuses to raise one for a crossing too brief to be real. Wraps `evaluate_warning()` rather than changing it, so the evaluator stays pure and its tests stay untouched. It reconciles two requirements that pull against each other — a 200 ms oil pressure dip must not be *missed* (it happens between two refreshes), but with no RPM input there is no honest low-pressure threshold, so a brief legitimate dip at idle must not *alarm*. They resolve because they are about different halves of the same event: a crossing must persist for `qualify_ms` before it counts at all, and once it counts it is held until acknowledged. `qualify_ms` of 0 gives latch-immediately, so it is opt-in. Acknowledging a still-present fault restarts qualification rather than re-raising on the next sample — dismissing a notice should buy at least that much quiet.

  `update()` both drives the latch and reports it, which is right for the one caller that ticks it; `state_at(idx)` reads the same answer back without advancing anything. The split exists because a view built only from the panels currently on screen would stop qualifying whatever is off screen — and the gauge product's zoom view shows one panel of three, so that is not hypothetical. The composition root ticks every signal on a timer, and [gui/bindings](../../gui/bindings/README.md) reads.

- **`inc/warning.hpp`** / **`src/warning.cpp`** — `evaluate_warning(value, thresholds)`: compares a `SignalValue` against a `WarningThresholds{lo, hi, use_lo, use_hi}`, gated by each bound's own on/off toggle and by `has_data` (so a signal can't false-trigger a warning before its first response). Lives here rather than in [core/config](../config/README.md) so this stays ignorant of how/where thresholds are persisted — config just stores a `WarningThresholds` per signal and hands it here.

## Usage

`core::SIGNAL_CATALOG_COUNT` sizes fixed arrays throughout the app — `SignalStore`'s value cache, `PeakHold` and `WarningLatch`'s per-signal state, `core::Config::signals[]` (see [core/config](../config/README.md)), and the `signal_names`/`signal_ids` tables the composition root builds for the Configurator/Signal Picker screens. It is **22 for the MQB product and 3 for the gauge**, which is why it is no longer a literal in `signal_catalog.hpp`: it lives in a generated `signal_catalog_count.inc` that the header includes, selected by include path. (An earlier version had `gen_catalog.py` regex-patch the count straight into the header — that cannot describe two products, and a header a script rewrites in place is a trap for whoever edits it next.) Adding an *active* signal means adding an entry to that product's registry with `"status": "active"` — or promoting an existing WIP one via the monitor tool — and re-running `tools/gen_catalog.py`. The generated `.inc`'s `static_assert` fails the build if the count and the array it sizes ever disagree.
