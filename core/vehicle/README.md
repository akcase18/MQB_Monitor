# core/vehicle/

The vehicle-signal data model: a static, ROM-able catalog of every signal the dashboard can display, the request scheduler that decides which of them to ask the ECU for, a runtime value store fed by decoded UDS responses, and signal-scoped warning-threshold evaluation.

## Files

- **`data/signals.json`** — the **two-stage signal registry**, single source of truth shared between this firmware and the Mac monitor tool ([tools/monitor](../../tools/README.md)). Every signal ever defined lives here, tagged `"status": "active"` or `"status": "wip"` (unconfirmed offset/scale, a placeholder name, etc.). `src/signal_catalog.cpp`'s `SIGNAL_CATALOG[]` array is **generated** by [`tools/gen_catalog.py`](../../tools/gen_catalog.py), which filters to `status == "active"` only — WIP entries never reach the firmware. The monitor tool's Registry/Learn/WIP tabs are how you add, review, and promote/demote entries; edit the JSON and re-run the script (commit both) if you're doing it by hand instead. Only the `transform_*` functions and unit helpers are hand-written in the `.cpp`; a signal's JSON `"transform"` field names one of them.

  Filtering **never reorders** the registry's own array order — active entries keep the same relative order they have in the file (`gen_catalog.py` just skips WIP ones, in place). The registry's order can still change, deliberately, via the monitor tool's Registry tab Move Up/Down (`Catalog.move_signal`). That's safe *today* only because `core::Config::signals[SIGNAL_CATALOG_COUNT]` (see [core/config](../config/README.md)) — a flat array persisted in flash, positionally indexed by the compiled catalog's array order (always resolved via `signal_catalog_find(id)`, never a raw index) — has never actually been written to a device (`ConfigStore::migrate()` is a no-op stub). Once a device has shipped with saved config, reordering active signals would misalign its already-saved on-device warning thresholds, and `migrate()` would need to stop being a no-op before that becomes routine.

- **`inc/signal_catalog.hpp`** / **`src/signal_catalog.cpp`** — `SIGNAL_CATALOG`, the *active* signals (generated from `data/signals.json`, above), each a `SignalSpec`:
  - `id`, `name`, `unit_type` (`UnitType::{None,Degrees,Percent,Pressure,RPM,Speed,Temp,Torque,Volume}`), `cycle_time_ms` (how often it's polled).
  - `requests[]`/`num_requests` — up to 2 `UdsRequestSpec`s (see [core/can](../can/README.md)) whose decoded values feed this signal.
  - `transform` — combines those decoded, already offset/scaled request values into the signal's final value. Most signals are a straight passthrough (`default`). A couple are **compound** signals combining two requests: `actual_intake_pressure` is bespoke hand-written C++, while `sum`/`difference`/`average`/`min`/`max` are generic two-request combiners meant for the monitor tool's Registry "New Compound Signal…" builder, which can produce a signal using any of them without touching C++ at all.
  - `display_min`/`display_max` — full-scale bounds in the signal's native (metric) unit. These are sensible engineering defaults (e.g. coolant 0–250°F equivalent, boost -15–25psi), **not** per-vehicle-tuned — they scale a Bar/Gauge panel's fill and bound the warning-threshold editor's +/- range. Real per-car tuning is a planned future phone-app feature, not built here (see [TODO.md](../../TODO.md)).

  Also: `signal_catalog_find(id)`, `signal_catalog_label()` (a signal's name as the dash's and phone's signal pickers list it — "Fuel (vol)" / "Fuel (%)" when two signals share a name), unit-label/decimal-precision helpers, and metric↔imperial conversion (`unit_convert_to_imperial`/`unit_convert_to_metric`) used both for display and for converting warning thresholds edited in whichever unit system a panel is currently showing.

  The current catalog: Coolant Temp, Engine Oil Temp, Intake Air Temp, Ambient Pressure, Charge Pressure, Intake Pressure (Actual), Intake Pressure (Specified), Engine Torque, Engine Speed (RPM), Throttle Position, Vehicle Speed, Fuel Level, per-cylinder (1–4) Misfire Count and Timing Correction, and a combined Misfire Count.

- **`inc/signal_store.hpp`** / **`src/signal_store.cpp`** — `SignalStore`, the runtime value cache:
  - `on_uds_response(byte1, byte2, raw, now_ms)` — the entry point fed by `UdsClient::poll()`. Finds every catalog request matching `(byte1, byte2)`, decodes it, and once *all* of a signal's requests have reported for this cycle, runs its `transform` and records the result.
  - `get(id)` / `get_display_value(id, is_metric)` — read a signal's current `SignalValue` (raw value, `has_data` flag, last-update timestamp) or its unit-converted, precision-rounded display value.

- **`inc/signal_poller.hpp`** / **`src/signal_poller.cpp`** — `SignalPoller`, which owns *what to ask for and when*:
  - `set_active(signal_ids, count)` — points it at the displayed panel set. **Only displayed signals are polled.** Everything else in the catalog is dead weight on the bus until the user puts it on a panel, and the displayed set is the complete demand: `gui::VehicleBinding::build_view_model()` and `core::Logger::sample()` are the only readers of live values, and both walk `Config::priorities[0..num_panels-1]`. Deduplicates DIDs across signals (Int Pres and Int Pres Act. both read `0x3E70`) at the faster of their cadences, since `SignalStore::on_uds_response()` already fans one response out to every catalog entry that owns the DID. Unchanged lists are a no-op, so `src/main.cpp` calls it both from each config-change callback and from a periodic backstop task.
  - `tick()` — called every `loop()` iteration, sends **at most one request, and only when nothing is outstanding**. A UDS server handles one request at a time, so this is what stops the tail of a burst being silently dropped by the ECU. Picks the most-overdue entry rather than walking the table in order, which is what keeps a slow signal from starving behind always-due fast ones when the ECU can't serve full demand.
  - `on_response()` / `on_negative_response()` — close the loop. A response frees the in-flight slot; so does a negative response, except NRC `0x78` (response-pending), which restarts the deadline instead. A DID that repeatedly times out or is rejected backs off to `BACKOFF_PERIOD_MS` so one unsupported identifier can't spend a response timeout every cycle forever.

  Replaced a one-`core::Scheduler`-task-per-catalog-entry model that polled all 22 signals regardless of what was on screen and fired each one's requests the instant its cycle timer came due, with nothing tracking whether the previous request had been answered. See the file doc comment for the numbers that made that fail on real hardware.

- **`inc/warning.hpp`** / **`src/warning.cpp`** — `evaluate_warning(value, thresholds)`: compares a `SignalValue` against a `WarningThresholds{lo, hi, use_lo, use_hi}`, gated by each bound's own on/off toggle and by `has_data` (so a signal can't false-trigger a warning before its first response). Lives here rather than in [core/config](../config/README.md) so this stays ignorant of how/where thresholds are persisted — config just stores a `WarningThresholds` per signal and hands it here.

## Usage

`core::SIGNAL_CATALOG_COUNT` (22 active, as of writing — `data/signals.json` may hold more WIP entries besides) sizes fixed arrays throughout the app — `SignalStore`'s value cache, `core::Config::signals[]` (see [core/config](../config/README.md)), and the `signal_names`/`signal_ids` tables `src/main.cpp` builds for the Configurator/Signal Picker screens. Adding an *active* signal means adding an entry to `data/signals.json` with `"status": "active"` (or promoting an existing WIP one via the monitor tool) and re-running `tools/gen_catalog.py`, which counts the active entries and syncs `SIGNAL_CATALOG_COUNT` in `signal_catalog.hpp` itself — no manual bump needed. The generated `.inc`'s `static_assert` fails the build if the count is ever stale.
