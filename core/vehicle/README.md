# core/vehicle/

The vehicle-signal data model: a static, ROM-able catalog of every signal the dashboard can display, the request scheduler that decides which of them to ask the ECU for, a runtime value store fed by decoded UDS responses, and signal-scoped warning-threshold evaluation.

## Files

- **`data/signals.json`** — the **two-stage signal registry**, single source of truth shared between this firmware and the Mac monitor tool ([tools/monitor](../../tools/README.md)). Every signal ever defined lives here, tagged with a status: `"active"` (compiled in and offered to the user), `"internal"` (compiled in for the firmware's own use but never offered — Dim Ctrl, which drives Auto brightness), or `"wip"` (unconfirmed offset/scale, a placeholder name, etc.). `src/signal_catalog.cpp`'s `SIGNAL_CATALOG[]` array is **generated** by [`tools/gen_catalog.py`](../../tools/gen_catalog.py): the active entries, then the internal ones — WIP entries never reach the firmware. Internal signals sit past `SIGNAL_CATALOG_COUNT` (the user-facing count), and `INTERNAL_SIGNAL_COUNT` follows them, so everything that walks the user-facing catalog — the saved per-signal config, the phone protocol and page, the signal picker, the logger — never sees them; `signal_catalog_find()` doesn't find their ids. Only `SignalStore` and `SignalPoller` serve the whole table (`SIGNAL_TABLE_COUNT`, looked up with `signal_table_find()`). They're held to the same validation as active ones (a name, a known unit, no clashing module ids), so promoting one to active is just a status change. It also generates `UDS_ECUS[]`, every module (`tx`/`rx` CAN ids) the active signals' requests go to, in order of first use; each request carries an index into it. It refuses an active request with no ECU, and two modules sharing a request or response id. The monitor tool's Registry/Learn/WIP tabs are how you add, review, and promote/demote entries; edit the JSON and re-run the script (commit both) if you're doing it by hand instead. Only the `transform_*` functions and unit helpers are hand-written in the `.cpp`; a signal's JSON `"transform"` field names one of them.

  Filtering **never reorders** the registry's own array order — active entries keep the same relative order they have in the file (`gen_catalog.py` just skips WIP ones, in place). The registry's order can still change, deliberately, via the monitor tool's Registry tab Move Up/Down (`Catalog.move_signal`). That's safe on dashes with saved settings: `core::Config::signals[]` (see [core/config](../config/README.md)) stores each signal's record with its id, and `ConfigStore::load()` puts the records back in catalog order on the next boot, so promoting, demoting or reordering never misaligns saved warning thresholds.

- **`inc/signal_catalog.hpp`** / **`src/signal_catalog.cpp`** — `SIGNAL_CATALOG`, the *active* signals (generated from `data/signals.json`, above), each a `SignalSpec`:
  - `id`, `name`, `unit_type` (`UnitType::{None,Angle,Percent,Pressure,RPM,Speed,Temp,Torque,Volume,Length,Voltage,Current,Illuminance,Time,TempDelta,Enum}` — append-only, since the ordinal goes over the wire to the phone configurator), `cycle_time_ms` (how often it's polled).
  - `enum_entries`/`num_enum_entries` — an `Enum` signal's value → label table (`EnumEntry { value, label }`), else `nullptr`/0. An Enum is a *state* (`signal_is_state()`): its panel shows `signal_enum_label()`'s label (or `?<n>` for a value with no label) with no unit, is always Digital, and has no warning thresholds — the configurator disables Bar/Gauge and Warning Thresholds for it. Labels are ASCII and at most `ENUM_LABEL_MAX` (15) characters, which `tools/gen_catalog.py` enforces. They're drawn in the theme's `data_text` font (bold 24, stepping down to fit a small panel): the big numeric fonts only carry digits, `-` and `.`.
  - `TempDelta` is a temperature *difference* — °C/°F with the ×1.8 but no +32. Pressure, Volume, Length, Voltage and Current round to their decimals; everything else truncates.
  - `requests[]`/`num_requests` — up to 2 `UdsRequestSpec`s (see [core/can](../can/README.md)) whose decoded values feed this signal.
  - `transform` — combines those decoded, already offset/scaled request values into the signal's final value. Most signals are a straight passthrough (`default`). A couple are **compound** signals combining two requests: `actual_intake_pressure` is bespoke hand-written C++, while `sum`/`difference`/`average`/`min`/`max` are generic two-request combiners meant for the monitor tool's Registry "New Compound Signal…" builder, which can produce a signal using any of them without touching C++ at all.
  - `display_min`/`display_max` — full-scale bounds in the signal's native (metric) unit. These are sensible engineering defaults (e.g. coolant 0–250°F equivalent, boost -15–25psi), **not** per-vehicle-tuned — they scale a Bar/Gauge panel's fill and bound the warning-threshold editor's +/- range. Real per-car tuning is a planned future phone-app feature, not built here (see [TODO.md](../../TODO.md)).

  Also: `signal_catalog_find(id)`, unit-label/decimal-precision helpers, and metric↔imperial conversion (`unit_convert_to_imperial`/`unit_convert_to_metric`) used both for display and for converting warning thresholds edited in whichever unit system a panel is currently showing.

  The current catalog: Coolant Temp, Engine Oil Temp, Intake Air Temp, Ambient Pressure, Charge Pressure, Intake Pressure (Actual), Intake Pressure (Specified), Engine Torque, Engine Speed (RPM), Throttle Position, Vehicle Speed, Fuel Level, per-cylinder (1–4) Misfire Count and Timing Correction, and a combined Misfire Count.

- **`inc/signal_store.hpp`** / **`src/signal_store.cpp`** — `SignalStore`, the runtime value cache:
  - `on_uds_response(byte1, byte2, payload, len, now_ms)` — the entry point fed by `UdsClient::poll()`. Every catalog request matching `(byte1, byte2)` reads its own `field` out of the payload and applies its offset/scale (a payload too short for a field leaves that request as it was), and once *all* of a signal's requests have reported for this cycle, runs its `transform` and records the result.
  - `get(id)` / `get_display_value(id, is_metric)` — read a signal's current `SignalValue` (raw value, `has_data` flag, last-update timestamp) or its unit-converted, precision-rounded display value.

- **`inc/auto_brightness.hpp`** / **`src/auto_brightness.cpp`** — `AutoBrightness`, the backlight level for `BrightnessMode::Auto` ([core/config](../config/README.md)): Dim Ctrl (`DIM_SIGNAL_ID`, the cluster's needle dimming curve, which follows the dimmer knob) taken as a percent — clamped to 0–100 first, since the byte can hold up to 255 — then shifted by the Settings slider (`shift_for()`: none at 50, ±`MAX_SHIFT_PCT` (25) at the ends, linear between), clamped to 0–100 again (0% is the backlight's dimmest visible duty, not off), and ramped at `RAMP_PCT_PER_S` so a knob step glides. With no reading for `STALE_MS` (ignition off, cluster asleep, a bench with no car) it heads for a fallback level instead — `src/main.cpp` passes the Day level, unshifted. `start()` sets where the ramp begins, so switching into Auto moves from the level the panel is at. `update(..., snap)` skips the ramp: `src/main.cpp` sets it while the panel is dark, so a night-time boot lights at the dimmer's level instead of lighting at Day and fading down. `src/main.cpp` adds Dim Ctrl to the poller's list only while Auto is on, and steps the ramp every 40 ms.

- **`inc/signal_poller.hpp`** / **`src/signal_poller.cpp`** — `SignalPoller`, which owns *what to ask for and when*:
  - `set_active(signal_ids, count, priority_count)` — points it at everything something reads live: the displayed panel set, Dim Ctrl while Auto brightness is on, and a log profile's signals while a Profile capture runs (`MAX_ACTIVE_SIGNALS` is six panels, sixteen profile signals and every internal signal). **Nothing else is polled.** The readers are `gui::VehicleBinding::build_view_model()`, `core::Logger::sample()` and the auto-brightness task, and `src/main.cpp` hands this the union of what they read. The first `priority_count` ids (the panels and Dim Ctrl) are **priority**; the rest are **background**. Deduplicates on (module, DID) across signals (Int Pres and Int Pres Act. both read `0x3E70`) at the faster of their cadences, priority if either signal is, since `SignalStore::on_uds_response()` already fans one response out to every catalog entry that owns it; the same DID number on two modules is two requests. One request is outstanding across the whole bus, whichever module it's for. Unchanged lists are a no-op, so `src/main.cpp` calls it both from each config-change callback and from a periodic backstop task.
  - `tick()` — called every `loop()` iteration, sends **at most one request, and only when nothing is outstanding**. A UDS server handles one request at a time, so this is what stops the tail of a burst being silently dropped by the ECU. Picks the most-overdue entry rather than walking the table in order, which is what keeps a slow signal from starving behind always-due fast ones when the ECU can't serve full demand. Priority entries go first: a background one is picked only when nothing priority is due, or once it has waited `BACKGROUND_STARVATION_MS` (1 s) past due, from when on it competes on overdue-ness. While background entries exist, a priority entry also keeps its schedule (`next_due += period`) after going out a little late behind a background request, instead of re-anchoring to the send time; otherwise every such wait would stretch its period, and logging would slow the panels after all. Measured against a fake ECU at ~66 answers/s: two 50 ms panels keep their full 20 Hz with two 50 ms log-only signals sharing the bus (those get ~13 Hz), where fair sharing would give all four ~17 Hz.
  - `on_response()` / `on_negative_response()` — close the loop. A response frees the in-flight slot; so does a negative response, except NRC `0x78` (response-pending), which restarts the deadline instead. While a multi-frame answer is part-way in (`UdsClient::receiving()`), the deadline stretches by up to `MULTI_FRAME_GRACE_MS` (200 ms), since each block of it needs a main-loop pass to drain. A DID that repeatedly times out or is rejected backs off to `BACKOFF_PERIOD_MS` so one unsupported identifier can't spend a response timeout every cycle forever.
  - `stats()` / `entry_stats(i)` / `reset_stats()` / `set_flood()` — for measuring the dash ([THROUGHPUT_TEST_PLAN.md](../../THROUGHPUT_TEST_PLAN.md)), behind `src/main.cpp`'s `POLLSTATS`/`STATSRESET`/`POLLFLOOD` serial commands. Totals are sent, answered, timed out, rejected and 0x78s. Each request-table entry also tracks its answers and the intervals between them, so its achieved period can be set against its target (a `set_active()` rebuild restarts those). Flood mode makes every entry due again the moment it's answered, so requests go out back to back; entries in back-off keep their slow retry.

  Replaced a one-`core::Scheduler`-task-per-catalog-entry model that polled all 22 signals regardless of what was on screen and fired each one's requests the instant its cycle timer came due, with nothing tracking whether the previous request had been answered. See the file doc comment for the numbers that made that fail on real hardware.

- **`inc/warning.hpp`** / **`src/warning.cpp`** — `evaluate_warning(value, thresholds)`: compares a `SignalValue` against a `WarningThresholds{lo, hi, use_lo, use_hi}`, gated by each bound's own on/off toggle and by `has_data` (so a signal can't false-trigger a warning before its first response). Lives here rather than in [core/config](../config/README.md) so this stays ignorant of how/where thresholds are persisted — config just stores a `WarningThresholds` per signal and hands it here.

## Usage

`core::SIGNAL_CATALOG_COUNT` (the active signals — `data/signals.json` may hold internal and WIP entries besides) sizes fixed arrays throughout the app — `SignalStore`'s value cache, the logger's per-signal state, and the `signal_names`/`signal_ids` tables `src/main.cpp` builds for the Configurator/Signal Picker screens. Adding an *active* signal means adding an entry to `data/signals.json` with `"status": "active"` (or promoting an existing WIP one via the monitor tool) and re-running `tools/gen_catalog.py`, which counts the active and internal entries and syncs `SIGNAL_CATALOG_COUNT` and `INTERNAL_SIGNAL_COUNT` in `signal_catalog.hpp` itself — no manual bump needed. The generated `.inc`'s `static_assert` fails the build if the count is ever stale. The saved config has a fixed 64 records (`core::SIGNAL_CONFIG_SLOTS`), so up to 64 signals can be active without touching the config layout; `gen_catalog.py` refuses more.
