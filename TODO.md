- [X] Data logging (record signal history via `platform::IStorage`) — [core/logging](core/logging/README.md)'s `Logger` records the currently-displayed signals (up to 6) on-change to a rotating ring of chunk files (oldest overwritten once full, ≥~3 hours retention worst-case), retrievable over USB via [tools/log_export](tools/log_export/README.md). Opt-in via `LoggingScreen` (swipe up from the dashboard; `Settings::logging_enabled`, off by default) so normal driving isn't spending flash write-cycles. That screen also reports captures saved, storage medium, capacity, and minutes recorded, and can erase the store on-device behind a confirm popup. - [ ] Size the log ring to the storage medium instead of a fixed 13MiB. `core::CHUNK_COUNT` (52) x `CHUNK_SIZE_BYTES` (256KiB) is a compile-time budget that doesn't consult the backend, so a Micro-SD card would use 13MiB of itself and leave the rest untouched — a 128GB card would sit 99.99% idle. Fine while onboard flash (~15.3MiB usable) is the only backend, and overkill capacity buys little in practice (1GiB is already ~8 days of worst-case continuous recording), but a card the user paid for should be usable. `Logger`'s constructor already takes both sizing parameters (the tests drive them) — `src/main.cpp` just passes the defaults, so this is mostly a matter of deriving them at boot. Needs a capacity query added back to `IStorage` (`LittleFS_Program::totalSize()` is O(1) mount arithmetic; SdFat's is `clusterCount() * bytesPerCluster()`, both cached volume metadata — avoid `freeClusterCount()`, which walks the FAT). Scale **chunk size** rather than chunk count: `begin()` opens every slot to read its header, so 4096 x 256KiB would mean 4096 file opens per boot, where 256 x 4MiB is the same ring for 256 opens (at the cost of coarser eviction granularity, irrelevant at that scale). Also needs `chunk_count_`'s `uint16_t` (65535 chunks = 16GiB at today's chunk size) and `MAX_LOG_ENTRIES` (128 tracked captures) revisited, plus a decision on what happens when a differently-sized card is swapped in mid-life, since `chunk_seq % chunk_count` remaps which slot a sequence lands in.

- [ ] **Revisit the 2026-08-25 cadence/refresh change if display smoothness or CAN freshness disappoints.** Everything moved together to make the dashboard feel responsive; these are the previous values, kept here so going back doesn't mean archaeology:

  | Constant | Was | Now | Where |
  |---|---|---|---|
  | `INFO_SCREEN_REFRESH_MS` | 200 (5Hz), then 100 (10Hz) | **50** (20Hz) | `src/main.cpp` |
  | `cycle_time_ms` for Int Pres (4), Engine Speed (7), Engine Torque (8), Throttle Pos (12), Int Pres Act. (22) | 20 | **50** | `core/vehicle/data/signals.json` — re-run `tools/gen_catalog.py` after editing |
  | `core::LOG_MIN_INTERVAL_MS` | 40 | **50** | `core/logging/inc/logger.hpp` |
  | `LOG_SAMPLE_PERIOD_MS` | 20 | **25** | `src/main.cpp` — kept at half the floor |

  **Superseded in part by `core::SignalPoller`** (see [core/vehicle](core/vehicle/README.md)): `cycle_time_ms` is now a *floor* rather than a fixed period. Requests are flow-controlled — one outstanding at a time, only for displayed signals — so a signal is polled no faster than its `cycle_time_ms` and slower whenever the ECU can't serve full demand. Lowering the five 50ms entries back to 20 would no longer put 20ms of traffic on the bus; it would just raise their share of whatever throughput the ECU actually gives. The `INFO_SCREEN_REFRESH_MS` and logging rows below still stand on their own.

  The 5Hz default came from Phase 6 of the rework (`c690f5c`) as an architectural default when "update the screen every loop iteration" became a scheduled task, not from a measured limit — the pre-rework code (`5e36824`) invalidated every panel label on *every* loop pass and let LVGL coalesce to its 20ms tick, so 50Hz redraws are known to have run on this panel. 20Hz is well inside that. Signals were raised to 50ms to match: polling faster than the display can restate a value only spends CAN bandwidth and time in the cooperative `loop()`, where `lv_timer_handler()`'s flush already competes with `uds_client.poll()`. (At the time this was the *only* thing bounding request rate, and it was not enough — see the hardware finding recorded under `core::SignalPoller`.) **Note the coupling to the backlight settle** (`BOOT_SETTLE_PASSES`, `BACKLIGHT_QUIET_MS` in `src/main.cpp`): boot counts render passes precisely so it doesn't depend on this rate, but the numbers in that comment block were measured at 200ms and 100ms.

- [ ] Let a host tool split a downloaded log into **captures**, not just sessions. `LOGDUMP` streams chunk files only, so [tools/log_export](tools/log_export/README.md) can group records by `session_id` (one power cycle) but has no way to see where one capture — a Logging on → off cycle, which is what `LoggingScreen` counts and what the user means by "a log" — ended and the next began. `/log_index.bin` isn't in the stream, and even read directly off a storage directory it only bounds a capture to a *chunk range*: several captures routinely share one chunk. Two ways out, both firmware-side: stream the index alongside the chunks (a `LOGINDEX` command, cheapest — but still only resolves to chunk granularity, so captures sharing a chunk stay merged), or write a capture-start marker record into the chunk itself (exact, but changes the on-disk format and so every reader of it). Worth doing whenever multi-capture drives become the normal case; today a session is a usable proxy.

- [ ] Wireless (phone) and Micro-SD export of the signal log — sequenced follow-ons to the USB-only retrieval above, both reusing the same on-disk `LogRecord`/`ChunkHeader` format over a different transport. Wireless needs new `remote::protocol` message types plus a chunking scheme (today's link is single-frame request/response only); Micro-SD needs a physical slot the current PCB doesn't have (the `TeensySdCard`/`IStorage` code path is already in place, see `platform/teensy/README.md`).
- [X] Wireless connectivity to a phone app for customization/setup — also the intended home for real per-vehicle range/threshold tuning (today's `SignalSpec::display_min/max` are sensible engineering defaults, not tuned per car). The SoftAP + QR-code hookup and the phone-facing config form ([gui/screens/inc/wireless_setup_screen.hpp](gui/screens/inc/wireless_setup_screen.hpp), [platform/esp32](platform/esp32/README.md)) both work end to end — the form covers everything the touchscreen does (brightness, panel/signal/units/display-mode assignment, warning thresholds) plus per-signal custom display-range, which has no touchscreen UI at all.
- [ ] ISO-TP support for CAN (multi-frame UDS responses) — current `core::can::UdsClient` only decodes single-frame responses.
- [ ] Firmware update strategy (OTA or otherwise).
- [ ] Expand to other vehicle platforms — the `platform/` HAL split and `core/vehicle` signal catalog make this architecturally possible, but the current catalog is still MQB-specific and no second platform is implemented.

It's a standalone sketch (`env:esp32c3`), not another `platform.hpp` `Platform` implementation — the C3 has no display/touch/CAN to back those interfaces.
